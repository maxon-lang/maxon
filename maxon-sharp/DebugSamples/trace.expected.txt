P4e DebugStream-CORRELATION gate — a stop shows the trace activity that led to it, and the NEXT stop
shows only what happened since. Reproducible transcript over DebugSamples/trace.maxon.

HOW TO REPRODUCE (from a checkout that has built the C# compiler):
  maxon build maxon-sharp/DebugSamples/trace.maxon --debugstream
  maxon build maxon-sharp/DebugSamples/step.maxon

RED (the same two command lines against a pre-P4e binary, before this rung): the word did not exist,
so a session could see a stop and could see nothing that led to it:
  {"event":"error","message":"unknown command 'trace'"}

WHAT EACH BLOCK PROVES (asserted by the JSON below):
  * block 1, first stop  -> the slice holds EXACTLY label(1)'s four mm events. The stop event carries
                            them automatically (orientation), and the explicit `trace` command answers
                            with the same window — the command re-asks a parked target, so the two
                            agree by construction rather than by one caching the other.
  * block 1, the STOP events -> the trace tail rides the stop itself (orientation, like the source
                            window and the backtrace), bounded to the most recent few with the number
                            it left out stated — `"traceOmitted":2` at the second stop. Both faces
                            apply that bound through one computation, so the transcript and the JSON
                            can never disagree about what a stop showed.
  * block 1, second stop -> THE WATERMARK TEST. Between the stops the program ran label(22), label(333)
                            and label(4444), and the slice holds those TWELVE events and NOT ONE of the
                            first stop's. A driver that re-rendered the ring would show sixteen here;
                            one with no watermark at all would show none. The window is a pair of ring
                            byte positions the AGENT recorded when it published each stop
                            (DbgOffStopDsMark), never a pair of timestamps — a stop parks the thread,
                            so a clock reading taken around one describes the debugger, not the program.
  * block 2              -> THE HONEST REFUSAL. step.exe is built WITHOUT --debugstream, so it has no
                            trace hooks at all and emits nothing. `trace` names the flag rather than
                            rendering an empty list, which would read as "nothing happened". Note the
                            shape: `"trace":null` plus a `traceUnavailable` reason, never `[]` — the
                            same rule the frame lists follow. Note also that the two `stop` events in
                            this block carry NO trace key: a binary with nothing to trace emits exactly
                            the shape it did before this rung, which is why the other 27 golden checks
                            are untouched by it.

WHAT IS STABLE vs BUILD-SPECIFIC:
  * The event TEXTS, their ORDER, and the two window SIZES (4 then 12) are the P4e subject and are
    STABLE: one processor, no async, and `n.toString()` allocates exactly one heap String per call, so
    the alloc ids run 1..4 in program order. The exit code 10 (byte lengths 1+2+3+4) is stable too.
  * The `.text` offsets (0xb5 / 0xfa the two breakpoints, 0x51 the entry-stub return, 0x9f in step.exe)
    are build-specific and move only if codegen moves.
  * NOT asserted, and deliberately: wall-clock deltas. The producer stamps every ring entry with one
    and `maxon monitor` prints it, because a live timeline is what it is watching; a stop-correlated
    slice states an ORDER and a WINDOW instead, so the driver's face carries no timestamp at all.

⚠ WHAT THIS GOLDEN DOES NOT COVER — only the `mm` family. The `sched` and `dbg` families carry raw
green-thread ADDRESSES in their payload, and `log` (the `__DebugStream` builtin) carries one too, so
none of them can appear in an exact-diff transcript. They decode through the same shared formatter that
`maxon monitor` uses, and monitor's own output is where they are exercised.
