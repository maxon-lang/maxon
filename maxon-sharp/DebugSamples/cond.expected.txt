P4d-1 conditional-breakpoint gate — reproducible transcript over DebugSamples/cond.maxon.

HOW TO REPRODUCE (from a checkout that has built the C# compiler):
  maxon build maxon-sharp/DebugSamples/cond.maxon
  maxon debug --batch --commands='break cond.maxon:32 if i == 4; run; print i; print doubled; print found; continue' maxon-sharp/DebugSamples/cond.exe
  maxon debug --batch --commands='break cond.maxon:32 if found == true; run; print i; print found' maxon-sharp/DebugSamples/cond.exe
  maxon debug --batch --commands='break cond.maxon:32 if i > 99; run' maxon-sharp/DebugSamples/cond.exe
  maxon debug --batch --commands='break cond.maxon:32 if label == 1; run' maxon-sharp/DebugSamples/cond.exe
  maxon debug --batch --commands='break cond.maxon:32 if missing == 1; run' maxon-sharp/DebugSamples/cond.exe
  maxon debug --batch --commands='break cond.maxon:32 if i == 4; break cond.maxon:32; run; print i' maxon-sharp/DebugSamples/cond.exe

RED (the same commands before this rung): `break … if …` did not exist. `break` passed the whole argument
to its file:line / function resolver, so every command above resolved the literal target
`cond.maxon:32 if i == 4`, failed TryParseFileLine (the trailing text defeats the `:line` parse), fell
through to the fuzzy function lookup, and emitted
  {"event":"breakpoint","action":"no-match","query":"cond.maxon:32 if i == 4"}
with NOTHING armed — followed straight by {"event":"exit","code":17}. No stop, no condition, no refusal
naming a reason.

WHAT EACH BLOCK PROVES (asserted by the JSON below):
  * BLOCK 1 — the condition is evaluated IN-PROCESS and is true on exactly one iteration. There is ONE
    stop event, not six: the breakpoint was hit on every iteration and the agent skipped five of them
    without ever waking the driver. `print i` = 4 confirms WHICH iteration was caught, and `print doubled`
    = 6 / `print found` = false confirm the frame really is iteration 4's (at the top of iteration i,
    `doubled` still holds i-1's result and `found` still holds (i-1) > 3) — so the stop is the right one,
    not merely a stop that happens to be at the right line. The trailing `continue` then runs to exit 17,
    proving the still-armed breakpoint kept skipping and that the skip path leaves the patched `.text`
    correct.
  * BLOCK 2 — a 1-byte operand. `found` is a bool the emitter parks at an UNALIGNED frame offset
    (rbp-0x11), so this exercises the agent's byte-at-a-time operand assembly and its unsigned width-1
    arm, not just the full-width load. It stops at i == 5, the first iteration on which `found` is true.
  * BLOCK 3 — a condition that is NEVER true produces NO stop at all, and the program still exits 17.
    This is the case that would silently pass if conditions were ignored and the driver merely filtered
    stops on its own side: here the driver is never told about the five hits in the first place.
  * BLOCK 4 — an unsupported OPERAND TYPE is REFUSED, unarmed. `label` is a String; the reply is
    action "condition-invalid" with a reason naming the type, and the program then runs to completion
    with no stop. A silently-unconditional breakpoint would have stopped at i == 0 instead.
  * BLOCK 5 — an unknown local is refused the same way, naming the local and the function.
  * BLOCK 6 — re-arming CLEARS a previous condition. `break … if i == 4` followed by a plain
    `break cond.maxon:32` reports an unconditional breakpoint and now behaves as one, stopping at i == 0.
    (This was a wrong answer found while writing this golden: the agent's set-breakpoint returns early
    when an address is already patched, so the slot's condition record survived, and the run kept skipping
    to i == 4 while the driver reported no condition. __dbg_set_bp now resets the condition on that path,
    so its postcondition is uniform: after it, a breakpoint is armed and unconditional.)

WHAT IS STABLE vs BUILD-SPECIFIC:
  * The event shapes, the STOP COUNT, the printed values, and the refusal reasons are the P4d-1 subject
    and are STABLE.
  * The `.text` offset (0xfe, the loop body's first statement; 0x51 the entry-stub return) is
    build-specific and moves only if codegen for `main` moves.
  * Exit code is 17 in EVERY block, including the refusals — a refused condition must leave the program
    running exactly as it would have without the command.
  * Non-ASCII characters in a reason string are emitted as JSON \u escapes by the writer, so the EXPECTED
    blocks below are pure ASCII and byte-comparable regardless of the console's encoding.
