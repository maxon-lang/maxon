P4d-2b green-thread CONTROL gate — reproducible transcript over DebugSamples/gtcontrol.maxon.

HOW TO REPRODUCE (from a checkout that has built the C# compiler):
  maxon build maxon-sharp/DebugSamples/gtcontrol.maxon
  maxon debug --target-env=MAXON_MAX_PROCS=1 --batch --commands='break gtcontrol.maxon:72; break gtcontrol.maxon:73; run; threads; gt-park 1; gt-park 4; threads; continue; threads; gt 4; gt 5; backtrace; locals; print mark; next; gt-resume 5; threads; continue' maxon-sharp/DebugSamples/gtcontrol.exe
  maxon debug --target-env=MAXON_MAX_PROCS=1 --batch --commands='break gtcontrol.maxon:72; break gtcontrol.maxon:73; run; threads; continue; threads; continue' maxon-sharp/DebugSamples/gtcontrol.exe

RED (the same commands against a pre-P4d-2b binary, before this rung): every control word was unknown,
so nothing could be parked, selected or read:
  {"event":"error","message":"unknown command 'gt-park'"}
  {"event":"error","message":"unknown command 'gt'"}
  {"event":"error","message":"unknown command 'gt-resume'"}
and the second block's transcript was ALREADY what it is below — which is the point of running it: it is
the CONTROL, and it is unchanged by this rung.

THE TWO BLOCKS ARE AN A/B, AND THAT IS WHAT PROVES THE PARK. They differ by one command, `gt-park 4`:
  * WITHOUT it, heldTask's await completes ~400 ms before the second breakpoint, so by then the thread
    has finished and the listing holds nothing but `main` (block 2).
  * WITH it, the scheduler is handed heldTask at that same moment and DECLINES it, so the thread is
    still alive and still parked at its await when the second breakpoint is reached (block 1).
No timing is asserted anywhere; the park's effect is a STATE, and the control run is what shows the
state is not simply what would have happened anyway.

WHAT EACH COMMAND PROVES (asserted by the JSON below):
  * gt-park 1        -> REFUSED by name. #1 is the processor's own inline scheduler thread, which is
                        never enqueued and so could never be caught by a hold; promising to park it
                        would be a promise nothing enforces.
  * gt-park 4        -> accepted, and the very next listing carries `hold":"held"` on that row — the
                        listing and the scheduler read the SAME predicate, so what the user is told and
                        what the scheduler does cannot disagree.
  * threads (after)  -> heldTask is STILL THERE, as `ready` + `parked` + `held`. Compare block 2, where
                        the same line of the same program lists only `main`.
  * gt 4             -> REFUSED, and ACTIONABLY: the id was minted before the resume, and ids are
                        re-minted on every resume, so the refusal names that rather than saying no such
                        thread exists. (P4d-2a listed this as a residual: correct but unfriendly.)
  * gt 5 / backtrace -> the context switch. The backtrace is heldTask's own, walked from ITS saved frame
                        pointer while the target is stopped in `main` — two frames, because a spawned
                        thread's chain ends at the spawn trampoline.
  * locals / print   -> ⭐ the frame is READ, not merely named: `i` and `mark` come out of heldTask's
                        parked frame at 41. `main` has no local called `mark` at all, so this value
                        cannot have come from the stopped thread.
  * next             -> REFUSED while another thread is selected. `gt` moves what the debugger LOOKS AT;
                        it cannot move what the target RUNS, and silently stepping the stopped thread
                        would report a stop about a thread the user was not looking at.
  * gt-resume 5      -> the hold column disappears from the next listing, and the program then RUNS TO
                        COMPLETION: exit 44 is heldTask's 42 (1 from innerTask + 41) plus freeTask's 2.
                        A park/resume round trip that leaked or wedged a thread could not produce it.

WHAT IS STABLE vs BUILD-SPECIFIC:
  * The thread set, each thread's kind/entry/status/cpu/hold, which thread is stopped, every refusal
    reason, the frame FUNCTIONS and LINES, the local VALUES (41), the id RELATIONSHIPS (#4 before the
    resume and #5 after, #1 stable across both stops) and the exit code 44 are the P4d-2b subject and
    are STABLE. Measured 20/20 byte-identical for each block.
  * The `.text` offsets are build-specific and move only if codegen moves. 0xf8fc — the spawn TRAMPOLINE
    frame — is RUNTIME code, so it moves whenever the emitted runtime changes size, not only when user
    codegen does.
    ⚠ It moved again, by 203 bytes, between P4d-2b (when this golden was recorded) and P7, and
    nothing caught it in between: this gate is not part of the per-rung battery. P7 measured the
    new value against a CLEAN origin/main build in its own worktree before touching it, so the
    drift was already on main and was not the profiler's doing.
  * NOT asserted, deliberately: the raw GreenThread addresses (they differ every run, which is why an id
    exists at all) and wall-clock timing.

⚠ RUN THE SAMPLE ONLY WITH MAXON_MAX_PROCS <= 2. `heldTask` spawns and awaits a green thread of its own,
and a NESTED async segfaults 100% of the time at 3 or more processors on the unchanged compiler — 20/20,
reproduced with `--no-debug-agent`, i.e. with none of this rung's code in the binary, and 0/20 at one or
two processors. That is a pre-existing scheduler defect (a sharper form of the intermittent
multi-processor spawn/await crash already filed in PLAN.md) and it is reported rather than fixed here.
The nesting is not decoration: a thread parked in `sleep` has `stdlib.sleep` as its top frame, whose
parameter is never spilled, so its locals are honestly empty and `print` would have nothing to read. A
thread parked in `await` has its OWN function as the top frame, which is what makes the selection
demonstrable at all.
