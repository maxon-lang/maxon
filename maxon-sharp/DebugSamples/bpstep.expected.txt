P4d-1 breakpoint-aware-stepping gate — reproducible transcript over DebugSamples/step.maxon.

Reuses the committed P4b sample: `main` -> `helper` -> `deeper`, exit 8. No new sample is needed, because
the defect is about the INTERACTION between a user breakpoint and a step command, not about new code
shapes.

HOW TO REPRODUCE (from a checkout that has built the C# compiler):
  maxon build maxon-sharp/DebugSamples/step.maxon
  maxon debug --batch --commands='break step.maxon:21; run; step; break step.maxon:10; finish; backtrace' maxon-sharp/DebugSamples/step.exe
  maxon debug --batch --commands='break step.maxon:21; run; step; break step.maxon:10; next' maxon-sharp/DebugSamples/step.exe
  maxon debug --batch --commands='break step.maxon:10; run; backtrace' maxon-sharp/DebugSamples/step.exe
  maxon debug --batch --commands='break step.maxon:21; run; step; break step.maxon:10; finish; finish; finish' maxon-sharp/DebugSamples/step.exe

RED (the same commands before this rung — the accepted P4b residual #1, "finish/next do not pause at a
user breakpoint hit during their run"):
  * BLOCK 1: `finish` sailed straight past the armed breakpoint at deeper:10 and reported
    {"event":"stop","reason":"breakpoint",...,"offset":"0xab","function":"main","line":21}, with the
    backtrace collapsed to `main:21 <- ?:?`. The breakpoint was armed (the `bp action=set` event is
    there) and deeper() really did run — the run simply did not stop in it.
  * BLOCK 2: `next` likewise reported {"reason":"step","function":"helper","line":16,"offset":"0x1d3"};
    the breakpoint at deeper:10 was never reported at all.
  * BLOCKS 3 and 4 are the CONTROL and the follow-on: block 3 was already correct before this rung and
    must stay byte-identical, which is what isolates the defect to the STEP machinery rather than to
    breakpoints themselves.

ROOT CAUSE (fixed here): MaxonDebugger.RunUntilReturn treated EVERY stop at an equal-or-deeper frame as
recursion re-entering its own armed return address, and continued past it. The user-breakpoint registry
(`_userBreakpointOffsets`) was consulted only at ARM time, never at STOP time.

WHAT EACH BLOCK PROVES (asserted by the JSON below):
  * BLOCK 1 — `finish` HONORS an intervening breakpoint. The run stops at deeper:10 with reason
    "breakpoint" (the agent published it as one; the driver did not invent a reason), and the following
    `backtrace` shows the full three-deep stack deeper:10 <- helper:15 <- main:21, proving the stop is in
    the callee frame and not a mislabeled stop in main.
  * BLOCK 2 — `next` honors it too. Step-over descends into deeper() via the same RunUntilReturn path, so
    it stops at deeper:10 with reason "breakpoint" instead of arriving at helper:16.
  * BLOCK 3 — CONTROL. A plain breakpoint at deeper:10 with no stepping was correct before this rung and
    is UNCHANGED by it. If this block ever moves, the fix has damaged ordinary breakpoints.
  * BLOCK 4 — the interrupted `finish` leaves a healthy session. After stopping at deeper:10, successive
    `finish` commands walk out one frame at a time: deeper:10 -> helper:15 (0x1d0) -> main:21 (0xab).
    (Note: that is ONE frame per finish. The original `finish` was abandoned when the breakpoint won, so
    reaching main again takes two more, not one.) Exit code stays 8, so the interception neither corrupts
    the program nor leaks a temp breakpoint patch.

WHAT IS STABLE vs BUILD-SPECIFIC:
  * The event shapes, functions, lines, reasons, and backtrace DEPTH are the P4d-1 subject and are STABLE.
  * The `.text` offsets (0x9f/0xab main's call and return, 0x1cb/0x1d0 helper's, 0x15c deeper's first
    statement, 0x4c the entry-stub return) are build-specific and move only if codegen for those
    functions moves.
  * Exit code is 8, identical to the P4b golden: honoring a breakpoint changes where the program STOPS,
    never what it computes.
