P6 CODE-COVERAGE gate — `maxon build --coverage` instruments, the program counts, `maxon coverage`
reports line AND branch coverage. Reproducible transcript over DebugSamples/coverage.maxon (a run that
completes) and DebugSamples/covpartial.maxon (a run that does not).

⭐ WHAT THIS GOLDEN IS FOR — THE THING NO LINE TABLE CAN DO. The `.mxdbg` line table holds
`(codeOffset, file, line, col, flags)`: no successor, no edge, no condition identity. An `if` with no
`else` therefore has NO ROW for the arm it does not take, and cannot have one — that arm has no source
text. Both `if`s below are exactly that shape, and block 1 reports `then@35=1 else(implicit)@35=2` and
`then@62=0 else(implicit)@62=1` for them. Instrumentation is the only place those numbers can come from.

⭐⭐ AND `match`, WHICH IS WHY THIS GOLDEN GREW. Arms are minted for `match` too — `weigh` has three,
one of them never taken — and they are reported as BRANCH ARMS, in `=== branches ===` and in the
`branches: n/m arms taken` summary, exactly like `then`/`else`. Before they were, this program reported
`lines: 2/2 covered`, `branches: 0/0 arms taken`, and BLANK next to every arm: three falsehoods at
once, the worst being a green 100% on code with an untested arm, because a green number gets trusted.
An arm's point carries TWO positions — its own, so `large gives 9` shows `#####` on ITS line, and its
construct's, so the three group into one branch.

It also puts all FOUR line states side by side, because three of them are easy to conflate:
  * a real COUNT (line 24 ran 3 times, line 25 once) — what the run did
  * `#####` (line 41) — real code the run never reached
  * `-----` (lines 19-20) — the optimizer emitted NO CODE for it (dead-function elimination removed
    `neverCalled` whole), which is a different fact from "untested" and must not be reported as one
  * blank (comments, blanks, every `end`) — no coverage point at all

HOW TO REPRODUCE (from a checkout that has built the C# compiler):
  maxon build maxon-sharp/DebugSamples/coverage.maxon --coverage
  maxon build maxon-sharp/DebugSamples/covpartial.maxon --coverage
  maxon coverage run maxon-sharp/DebugSamples/coverage.exe
  maxon coverage run maxon-sharp/DebugSamples/coverage.exe --json
  maxon coverage run maxon-sharp/DebugSamples/covpartial.exe

RED (the same command lines against a pre-P6 binary): `maxon coverage` was not a command at all — it
fell through to the usage text and exit 1 — and `--coverage` was not a build flag, so the build lines
above were rejected as unknown options. There were no counters, no `.mxcov`, and the sidecar's
coverage-point slots were written as zero with the comment "Coverage section slots stay 0 until P6".

WHAT EACH BLOCK PROVES (asserted by the output below):
  * BLOCK 1 — THE HEADLINE. The annotated listing, with all four states and all three branches. Note
    `classify`'s line 35 at 3 and line 39 at 2: the `if` header runs three times, and the fall-through
    below it twice, which is the implicit else arm counted from the other direction. Note `weigh`'s
    line 43 at 2 while its arms read 1, 1 and `#####` — the dispatch ran twice and reached two of its
    three cases. Note also that every executable line carries its OWN count: the line table for this
    same program has rows for only some of them, because a statement whose code is folded away leaves
    no row behind while its coverage point still counts the line's executions.
  * An arm renders as `<kind>@<line>=<count>`, one shape for `then`, `else` and `case` alike, each
    naming the line to look at — which for an `else` is not the `if`'s.
  * `target exit code:` is the MEASURED PROGRAM's status, reported as DATA. `maxon coverage` still
    exits 0 here: its own exit code answers "did the measurement complete", and one integer cannot
    answer two questions. The debug face settles the policy — `maxon debug --batch` emits
    `{"event":"exit","code":N}` and itself exits 0 for exactly the same reason. Block 3 is the case
    where this tool's own exit DOES go non-zero, and it is not the program's status that makes it:
    the run never finished, so there is no completed measurement to report.
  * BLOCK 2 — THE SAME REPORT AS JSON, from the same model through the second renderer. The two faces
    are a text renderer and a JSON renderer over ONE report; there is no second aggregation.
  * BLOCK 3 — PARTIAL. covpartial panics halfway, so the dump runs from the panic path and marks the
    data ABORTED. The report says the run did not complete and `maxon coverage` exits NONZERO: the
    counts are real, but presenting a truncated run as a finished measurement is what an instrument
    must not do. `neverReached` is `-----` here for the same reason `neverCalled` is in block 1.
  * BLOCK 4 — A DATA FILE FROM A DIFFERENT BUILD IS REFUSED. A counter is an anonymous index, so
    joining another binary's numbers to this binary's point table would name real source lines with
    counts belonging to other lines. It is refused on the build-id, exactly as the sidecar is.
  * BLOCK 5 — `--coverage --no-debug-info` IS REFUSED BY NAME (E5003). The counters are meaningless
    without the sidecar's point table to interpret them, so the combination cannot produce a readable
    artifact and is rejected rather than half-honoured. The check runs AHEAD of the build cache: a
    cached binary must not be handed back for a request that should have been refused.

WHAT IS STABLE vs ENVIRONMENT-SPECIFIC:
  * Every count, state, branch arm and total is the P6 subject and is STABLE: pure integer arithmetic,
    no stdlib calls, no green threads, so the program executes exactly the same statements every run.
  * Paths are printed RELATIVE to the working directory, so this transcript is the same on every
    machine. Run the commands from the repository root, as the gate does.
  * No addresses, no timings, no session ids appear anywhere in a coverage report.
