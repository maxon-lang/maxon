P6 COVERAGE-over-MCP gate — the SAME report an agent asks for, through `maxon mcp`.

⭐ WHAT THIS GOLDEN IS FOR. `coverage.expected.txt` proves the measurement; this one proves there is
exactly ONE of it. The `coverage` family builds through the same `DebugBuild.Compile` the debug family
uses (stating `--coverage` rather than inheriting it, for the reason `debug_start` states
`--debugstream`), runs and joins through the same `CoverageRunner`, and renders through the same
`CoverageRender.Json` that `maxon coverage --json` prints. Compare the numbers below against block 2 of
`coverage.expected.txt`: they are equal because they come from one report model through one renderer,
not because two aggregations happen to agree.

`coverage_report` re-reads the data an earlier run wrote WITHOUT running the program again, which is
what makes the join separable from the run — an agent that ran its program itself can still ask for the
report, and CI can aggregate.

HOW TO REPRODUCE (from a checkout that has built the C# compiler):
  maxon build maxon-sharp/DebugSamples/coverage.maxon --coverage
  maxon mcp --port=47822 --idle-timeout=120
  S=$(curl -sS -D- -o/dev/null -H 'Content-Type: application/json' -d '{"jsonrpc":"2.0","id":0,"method":"initialize","params":{}}' http://127.0.0.1:47822/mcp | tr -d '\r' | awk '/^Mcp-Session-Id:/{print $2}'); for m in '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"coverage_run","arguments":{"source":{"kind":"file","path":"maxon-sharp/DebugSamples/coverage.maxon"}}}}' '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"coverage_report","arguments":{"source":{"kind":"file","path":"maxon-sharp/DebugSamples/coverage.maxon"}}}}'; do curl -sS -H "Mcp-Session-Id: $S" -H 'Content-Type: application/json' -d "$m" http://127.0.0.1:47822/mcp; echo; done

RED (the same command line against a pre-P6 binary): `tools/list` advertised thirteen `debug_*` tools
and nothing else; `coverage_run` came back as an unknown tool.

WHAT THIS BLOCK PROVES:
  * `coverage_run` builds WITH instrumentation, runs the program, and answers with the report — one
    call, no live session to hold, so unlike a debug session nothing here outlives the request.
  * The report is SPLICED as raw JSON under `coverage`, never re-encoded as a string: it is already
    the one renderer's output, and wrapping it would hand an agent JSON to parse twice.
  * `coverage_report` answers with the identical numbers without re-running — the join is a separate
    step from the run, and both are the same two lines of driver code either face calls.
  * The four line states and every branch arm travel to an agent as FIELDS, not as prose:
    `linesEliminated`, `armsTaken`/`armsInstrumented`, and a `branches[].arms[]` array in which each
    arm names its `kind` (`then` / `else` / `case`), its own line, and either a `count` or
    `state:"eliminated"`. `implicit` appears only on the arm the source never wrote — a field that
    read false on every `case` and every `then` would be a column of one value, not a fact.

WHAT IS STABLE vs ENVIRONMENT-SPECIFIC:
  * Every count and state is the P6 subject and is STABLE (see coverage.expected.txt).
  * `Mcp-Session-Id` is fresh per run and is deliberately never printed — it is captured into a shell
    variable and echoed back as a header.
  * The port is FIXED at 47822 rather than chosen, for the reason mcp.expected.txt gives: a server
    that silently moved would mean a configured client talking to something else.
