P4d-2a green-thread VISIBILITY gate — reproducible transcript over DebugSamples/threads.maxon.

HOW TO REPRODUCE (from a checkout that has built the C# compiler):
  maxon build maxon-sharp/DebugSamples/threads.maxon
  maxon debug --target-env=MAXON_MAX_PROCS=1 --batch --commands='break threads.maxon:39; break threads.maxon:50; run; threads; gt-backtrace 3; gt-backtrace 1; gt-backtrace 9; continue; threads' maxon-sharp/DebugSamples/threads.exe

RED (the same command against a pre-P4d-2a binary, before this rung): `threads` and `gt-backtrace` were
unknown words, and --target-env did not exist, so the run produced no thread information at all:
  maxon debug: Unknown 'maxon debug' option: --target-env=MAXON_MAX_PROCS=1
and without that flag, with the commands alone:
  {"event":"error","message":"unknown command 'threads'"}
  {"event":"error","message":"unknown command 'gt-backtrace'"}

WHAT EACH COMMAND PROVES (asserted by the JSON below):
  * threads (first)  -> the enumeration is a UNION and BOTH halves are present. #1 is `kind:"scheduler"`,
                        main's own green thread, which lives INLINE in the processor struct and is never
                        linked into `__gt_all_head` — a list built from the spawned-thread list alone
                        would omit it. It is also `cpu:"stopped"`, i.e. the thread the debugger is
                        stopped on, so the omitted half IS the stopped one. #2/#3 are the two spawned
                        tasks, `cpu:"parked"`, each with a top frame in the sleep they are waiting in.
  * status vs cpu    -> reported SEPARATELY and they disagree on purpose: #1 reads `status:"running"`
                        (the runtime sets that before switching INTO a thread and never clears it) while
                        #2/#3 read `waiting`. `cpu` is the debugger's own question — which thread a
                        processor is actually executing — and it is what gates a stack walk.
  * gt-backtrace 3   -> a PARKED thread's stack is walked from its own saved frame pointer, bounded by
                        its own stack extent: sleep <- slowTask:22 <- the spawn trampoline. Frame 0 is a
                        RETURN ADDRESS (a parked thread has no trapped PC), so it carries the call-site
                        bias like any other non-zero frame.
  * gt-backtrace 1   -> the STOPPED thread is answered from the exact trapped PC instead, so its frame 0
                        is main:39 rather than a return address — the one on-cpu thread whose stack is
                        standing still.
  * gt-backtrace 9   -> an id nobody holds is REFUSED by name; it is never answered with an empty stack,
                        which a consumer would read as "this thread has no frames".
  * threads (second) -> THE ID TEST. Between the two stops the first pair of threads COMPLETED and their
                        structs went back on the processor's free list, where the next two spawns pop
                        them straight off — measured: the same addresses come back, and for a repeated
                        entry function they come back with the same entry function too. The second pair
                        is nevertheless #4/#5, never #2/#3: an id is scoped to the driver's resume count,
                        so it cannot outlive the target running. #1 keeps its id across both stops
                        because a processor's inline thread cannot be recycled at all.

WHAT IS STABLE vs BUILD-SPECIFIC:
  * The thread set, each thread's kind/entry/status/cpu, which thread is stopped, the frame FUNCTIONS and
    LINES, the id RELATIONSHIPS (#1 stable across both stops, #4/#5 distinct from #2/#3), and the exit
    code 6 (1+2 from the first pair, 1+2 from the second) are the P4d-2a subject and are STABLE.
  * The `.text` offsets (0x115/0x1a5 the two breakpoints, 0x238 inside sleep, 0x274 slowTask's sleep call,
    0x4c the entry-stub return) are build-specific and move only if codegen moves. ⚠ So is 0xf8e3, the
    spawn TRAMPOLINE frame in the two per-thread backtraces — and unlike the others it is RUNTIME code,
    so it moves whenever the emitted runtime changes size, not only when user codegen does. It was 0xf7ed
    until P4d-GT-STACK added __gt_stack_high and the stack-extent bounds to the frame walkers.
    ⚠ It moved again, by 203 bytes, between P4d-2b (when this golden was recorded) and P7, and
    nothing caught it in between: this gate is not part of the per-rung battery. P7 measured the
    new value against a CLEAN origin/main build in its own worktree before touching it, so the
    drift was already on main and was not the profiler's doing.
  * NOT asserted, and deliberately: the raw GreenThread addresses (they differ every run, which is why an
    id exists at all) and wall-clock timing.

⚠ WHAT THIS GOLDEN DOES NOT COVER — `--target-env=MAXON_MAX_PROCS=1` pins the debuggee to a SINGLE
processor, and that is what makes the transcript byte-stable: with the default setting the scheduler
spawns worker processors on demand, so the number of `kind:"scheduler"` rows is machine- and
timing-dependent and no exact-diff golden is possible. The consequence is that MULTI-PROCESSOR
enumeration is NOT exercised here, and neither is the one refusal that needs it — a thread found RUNNING
on another processor, which `gt-backtrace` declines to walk because its saved rsp/rbp are stale. Both
belong to P4d-2b, which introduces per-thread park/resume and can hold a thread in that state
deterministically. The single-processor run still exercises both halves of the union, both sides of the
park gate (the stopped thread on-cpu, two spawned threads parked), and the id-recycling test above.
