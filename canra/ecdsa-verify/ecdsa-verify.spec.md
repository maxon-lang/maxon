## Overview

This spec defines ECDSA signature verification (FIPS 186-5 section 6.4.2) for the two curve and hash pairs TLS 1.3 uses, as one function:

- **verify** -- checks a DER-encoded ECDSA signature over a message against an uncompressed public key, on P-256 with SHA-256 (`ecdsa_secp256r1_sha256`) or P-384 with SHA-384 (`ecdsa_secp384r1_sha384`).

The function hashes the message itself; the hash is fixed by the curve. It returns `true` or `false` for every well-formed input and an error only when an input cannot be parsed or is not supported.

**Out of scope:** signing (the `ecdsa-sign-p256` spec), other curves (P-521, secp256k1, Brainpool), other hash pairings (P-256 with SHA-384, truncated hashes), verification of a precomputed digest, compressed public keys, public keys wrapped in SubjectPublicKeyInfo or certificates, raw `r || s` (IEEE P1363) signatures, and BER signatures.

## Types

### EcdsaError

```pseudocode
type EcdsaError =
  | UnsupportedCurve           // curve is not "p256" or "p384"
  | InvalidPublicKey           // public_key is not an uncompressed SEC 1 point on the curve
  | InvalidSignatureEncoding   // signature_der is not a strict DER ECDSA-Sig-Value with non-negative integers
```

### Curves

| `curve` | Curve | Hash | Coordinate and scalar size | Public key length |
|---|---|---|---|---|
| `"p256"` | P-256 (secp256r1) | SHA-256 | 32 bytes | 65 bytes |
| `"p384"` | P-384 (secp384r1) | SHA-384 | 48 bytes | 97 bytes |

Both curves are `y^2 = x^3 - 3x + b` over `GF(p)` with prime order `n` and cofactor 1 (SP 800-186 sections 3.2.1.3 and 3.2.1.4):

### Public key encoding

`04 || x || y` (SEC 1 section 2.3.3), with `x` and `y` big-endian and exactly the coordinate size each, `x < p`, `y < p`, and `(x, y)` on the curve. This is the point a TLS certificate's SubjectPublicKeyInfo carries in its BIT STRING.

### Signature encoding

```pseudocode
ECDSA-Sig-Value ::= SEQUENCE { r INTEGER, s INTEGER }
```

encoded in DER (X.690 section 10). The strict-DER rules this spec requires are:

1. The input is exactly one TLV with tag `0x30` (SEQUENCE); no bytes follow it.
2. Every length is definite and minimal: a length below 128 uses the one-byte short form; a length of 128 or more uses the long form `0x80 | k` followed by `k` big-endian length bytes with no leading zero byte. The indefinite form `0x80` is rejected.
3. The SEQUENCE contains exactly two TLVs, each with tag `0x02` (INTEGER), and nothing else.
4. Each INTEGER has at least one content byte and is minimally encoded: a first byte `00` is allowed only when the next byte is `80` or above.
5. Each INTEGER is non-negative: its first content byte is below `80`. A negative INTEGER is an encoding error, not an out-of-range value.

A signature that breaks any rule is `InvalidSignatureEncoding`. A signature that follows them but has `r` or `s` outside `[1, n - 1]` (zero, or `n` or more, including INTEGERs longer than the curve size) is well formed and verifies as `false`.

## Functions

### verify

```pseudocode
verify(curve: String, public_key: Bytes, message: Bytes, signature_der: Bytes) -> Bool | EcdsaError
```

**Parameters:**

| Name | Type | Required | Description |
|---|---|---|---|
| `curve` | String | yes | `"p256"` or `"p384"`, exactly (lowercase, no hyphen) |
| `public_key` | Bytes | yes | The signer's public key, uncompressed SEC 1 point |
| `message` | Bytes | yes | The signed message, any length; hashed by this function |
| `signature_der` | Bytes | yes | The DER-encoded ECDSA-Sig-Value |

**Returns:** `true` if the signature is valid, `false` if it is well formed but not valid, or `UnsupportedCurve`, or `InvalidPublicKey`, or `InvalidSignatureEncoding`.

**Algorithm:**

1. If `curve` is not `"p256"` or `"p384"`, return `UnsupportedCurve`. Select the curve parameters, the hash `H` and the size `L` (32 or 48).
2. If `length(public_key) != 1 + 2L` or `public_key[0] != 0x04`, return `InvalidPublicKey`. Let `x` and `y` be the next two `L`-byte big-endian integers. If `x >= p`, `y >= p`, or `y^2 != x^3 - 3x + b (mod p)`, return `InvalidPublicKey`. Let `Q = (x, y)`.
3. Parse `signature_der` under the strict-DER rules; on failure return `InvalidSignatureEncoding`. Let `r` and `s` be the two integers.
4. If `r < 1`, `r > n - 1`, `s < 1` or `s > n - 1`, return `false`.
5. `e = int(H(message))`, big-endian. The hash and the order have the same bit length, so no truncation applies.
6. `w = s^(-1) mod n`; `u1 = e * w mod n`; `u2 = r * w mod n`.
7. `R = u1 * G + u2 * Q`. If `R` is the point at infinity, return `false`.
8. Return `R.x mod n == r`.

## Behavioral Contracts

### verify()

**MUST:**

1. MUST return `true` exactly when FIPS 186-5 section 6.4.2 accepts `(r, s)` for `H(message)` and `Q`, and `false` for every other well-formed input.
2. MUST check, in order, the curve name, the public key, then the signature encoding, and return the first error found. Range checks on `r` and `s` come after parsing and give `false`.
3. MUST hash `message` with the curve's hash. It MUST NOT accept a digest in place of the message, or any other hash.
4. MUST apply the strict-DER rules exactly: BER forms (long-form lengths below 128, lengths with leading zero bytes, the indefinite form), extra leading zero bytes, negative integers, wrong tags, missing or extra elements, and trailing bytes after the SEQUENCE are all `InvalidSignatureEncoding`.
5. MUST return `false`, not an error, when `r` or `s` is 0 or at least `n`; it MUST NOT reduce them modulo `n`.
6. MUST accept both `s` and `n - s`: FIPS 186-5 verification does not require low-S, and TLS signers do not normalize it.
7. MUST reject public keys as `InvalidPublicKey` exactly as `ecdh-p256` does: the identity, compressed and hybrid forms, wrong lengths (a P-256 key passed with `"p384"` and the reverse), coordinates at least `p`, and points off the curve.
8. MUST compute `R` correctly when `u1 * G` and `u2 * Q` are equal, negatives of each other, or `R` is the point at infinity (Wycheproof `point-duplication` and `edge-case-shamir-multiplication`), and when `u1` or `u2` is 0 or small (Wycheproof `small-rand-s`, `modular-inverse`, `arithmetic-error`).

**MAY:**

1. MAY run in variable time: verification uses only public data. A shared scalar-multiplication routine that is constant time is also correct.

## Test Vectors

`curve` is a string; `public_key_hex`, `message_hex` and `signature_der_hex` are lowercase hex. Expected output is `result` (`true` or `false`) or an `error`. Tags `p256` and `p384` give the curve.

### Sources

- `nist-cavp` vectors are every record of the `[P-256,SHA-256]` and `[P-384,SHA-384]` sections of `SigVer.rsp` in NIST CAVP `186-4ecdsatestvectors.zip` (CAVS 11.0; FIPS 186-5 verification is unchanged from FIPS 186-4): 15 records each, with `Qx`, `Qy` given here as the uncompressed point and `R`, `S` as their DER encoding. `Result = P` records expect `true`; `F` records, with the reason as a tag (`message-changed`, `q-changed`, `r-changed`, `s-changed`), expect `false`.
- `wycheproof-tc-N` vectors are from Project Wycheproof `testvectors_v1/ecdsa_secp256r1_sha256_test.json` and `ecdsa_secp384r1_sha384_test.json` (test-case id `N` within its file, tagged with the curve). The subset is the first 5 test cases, in tcId order, of each distinct combination of result and flags in each file: 84 of the 484 P-256 cases and 84 of the 504 P-384 cases. All 988 were checked.
  Every `valid` case expects `true`. Every `invalid` case expects `false` or `InvalidSignatureEncoding`, as the strict-DER rules decide; Wycheproof does not separate the two.
- `constructed` vectors are built for this spec from the first passing NIST P-256 record (`unsupported-curve`, `invalid-public-key`, `invalid-signature-encoding`, `out-of-range`, `check-order`, `malleability`, `modified-message`); `wrong-curve-length` also uses the first passing P-384 record's key.
- Every expected value was computed by two independent implementations, which agreed, and matched its published source. Two independent strict DER decoders agreed on every signature.

## Edge Cases

- **Empty message.** Valid; the hash of the empty string is signed. Wycheproof tc 1 of each file is one.
- **`r` or `s` with a leading `00`.** Required when the integer's top bit is set, forbidden otherwise.
- **Short `r` or `s`.** An integer with leading zero bytes in its fixed-size form is encoded shorter; the signature is shorter than usual and valid.
- **`r` or `s` equal to 0 or `n`, or `r + n`.** Well formed and `false`.
- **High-S signatures.** `(r, n - s)` verifies whenever `(r, s)` does: ECDSA signatures are malleable, and this spec does not reject either form.
- **A P-256 key with `"p384"`.** `InvalidPublicKey` (wrong length), even if the signature would verify on P-256.
- **Both a bad key and a bad signature.** `InvalidPublicKey`: the key is checked first.

## Implementation Notes

- **Parse, then check range.** Keep the two steps separate: parsing decides `InvalidSignatureEncoding`, the range check decides `false`. A parser that silently accepts a negative INTEGER as a large positive one, or that reduces `r` modulo `n`, fails the Wycheproof vectors.
- **Length limits.** A P-256 signature is at most 72 bytes and a P-384 signature at most 104. A parser MAY reject longer inputs early as long as the result is the same as the full rules give: for example, an over-long but well-formed INTEGER is out of range, so `false`, not an encoding error.
- **Double-scalar multiplication.** `u1 * G + u2 * Q` with Shamir's trick (interleaved windows) is about twice as fast as two separate multiplications. Use formulas that handle doubling and the point at infinity (complete formulas, or explicit checks: verification is not secret, so branches are allowed).
- **Comparison.** Compare `R.x mod n` with `r`; for both curves `p > n`, so `R.x` can be at least `n` and the reduction matters.
- **TLS.** TLS 1.3 `CertificateVerify` with `ecdsa_secp256r1_sha256` passes the 64 spaces, context string and transcript hash as `message`; the certificate's SubjectPublicKeyInfo supplies the point.
