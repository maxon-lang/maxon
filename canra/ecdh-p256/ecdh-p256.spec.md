## Overview

This spec defines elliptic-curve Diffie-Hellman over the NIST P-256 curve (secp256r1), as the ECC CDH primitive of NIST SP 800-56A section 5.7.1.2 with cofactor 1, in two functions:

- **public_key** -- returns the public key `d * G` of a private key `d`, as an uncompressed SEC 1 point.
- **shared_secret** -- returns the shared secret `Z`, the x-coordinate of `d * Q`, for a private key `d` and a peer's public key `Q`, after validating `Q`.

These are the operations a TLS 1.3 endpoint performs for the `secp256r1` key share (RFC 8446 section 4.2.8.2): it sends `public_key(d)` and derives the shared secret from the peer's key share with `shared_secret`.

**Out of scope:** key generation (choosing `d` uniformly from `[1, n - 1]` with a secure random source is the caller's job), compressed and hybrid point encodings, other curves, X25519, cofactor variants for curves with a cofactor other than 1, key derivation from `Z` (the `hkdf` spec), and ephemeral-key management.

## Types

### EcdhError

```pseudocode
type EcdhError =
  | InvalidPrivateKey   // the private key is not 32 bytes, or its value is 0 or at least n
  | InvalidPublicKey    // the peer public key is not an uncompressed SEC 1 encoding of a point on P-256
```

### Curve P-256

The curve is `y^2 = x^3 + a*x + b` over the prime field `GF(p)`, with a base point `G` of prime order `n` and cofactor 1 (SP 800-186 section 3.2.1.3):

```pseudocode
p  = 0xffffffff00000001000000000000000000000000ffffffffffffffffffffffff
a  = p - 3
b  = 0x5ac635d8aa3a93e7b3ebbd55769886bc651d06b0cc53b0f63bce3c3e27d2604b
Gx = 0x6b17d1f2e12c4247f8bce6e563a440f277037d812deb33a0f4a13945d898c296
Gy = 0x4fe342e2fe1a7f9b8ee7eb4a7c0f9e162bce33576b315ececbb6406837bf51f5
n  = 0xffffffff00000000ffffffffffffffffbce6faada7179e84f3b9cac2fc632551
```

### Encodings

| Value | Encoding |
|---|---|
| Private key `d` | Exactly 32 bytes, the big-endian integer `d`; valid when `1 <= d <= n - 1` |
| Public key `(x, y)` | Exactly 65 bytes: `04 || be32(x) || be32(y)` (SEC 1 section 2.3.3, uncompressed), with `x < p` and `y < p` |
| Shared secret `Z` | Exactly 32 bytes: `be32(x)` of the shared point, leading zero bytes kept (SP 800-56A section 5.7.1.2, SEC 1 section 2.3.5) |

`be32(v)` is `v` as a 32-byte big-endian integer. The point at infinity has no 65-byte encoding; its SEC 1 encoding is the single byte `00`, which `shared_secret` rejects.

## Functions

### public_key

```pseudocode
public_key(private_key: Bytes) -> Bytes | EcdhError
```

**Parameters:**

| Name | Type | Required | Description |
|---|---|---|---|
| `private_key` | Bytes | yes | The private key, 32 bytes big-endian |

**Returns:** The 65-byte uncompressed public key, or `InvalidPrivateKey`.

**Algorithm:**

1. If `length(private_key) != 32`, return `InvalidPrivateKey`.
2. `d = int(private_key)` (big-endian). If `d == 0` or `d >= n`, return `InvalidPrivateKey`.
3. `(x, y) = d * G`.
4. Return `04 || be32(x) || be32(y)`.

### shared_secret

```pseudocode
shared_secret(private_key: Bytes, peer_public_key: Bytes) -> Bytes | EcdhError
```

**Parameters:**

| Name | Type | Required | Description |
|---|---|---|---|
| `private_key` | Bytes | yes | The caller's private key, 32 bytes big-endian |
| `peer_public_key` | Bytes | yes | The peer's public key, 65 bytes, uncompressed |

**Returns:** The 32-byte shared secret `Z`, or `InvalidPrivateKey`, or `InvalidPublicKey`.

**Algorithm:**

1. Validate `private_key` as `public_key` steps 1 and 2 do; on failure return `InvalidPrivateKey`.
2. If `length(peer_public_key) != 65` or `peer_public_key[0] != 0x04`, return `InvalidPublicKey`.
3. `x = int(peer_public_key[1 .. 32])`, `y = int(peer_public_key[33 .. 64])`. If `x >= p` or `y >= p`, return `InvalidPublicKey`.
4. If `y^2 != x^3 + a*x + b (mod p)`, return `InvalidPublicKey`.
5. `P = d * (x, y)`. Because the cofactor is 1 and `(x, y)` is a point on the curve other than the point at infinity, `P` is never the point at infinity for `1 <= d <= n - 1`.
6. Return `be32(P.x)`.

Steps 2 to 4 are the full public-key validation of SP 800-56A section 5.6.2.3.3 for a curve of prime order: the point is not the identity, its coordinates are in range, it is on the curve, and `n * Q` is the identity (true of every point on a prime-order curve, so it needs no computation).

## Behavioral Contracts

### public_key()

**MUST:**

1. MUST return `04 || be32(x) || be32(y)` of `d * G`, 65 bytes, for every `d` in `[1, n - 1]`.
2. MUST return `InvalidPrivateKey` for a private key that is not exactly 32 bytes or whose value is 0 or at least `n`. It MUST NOT reduce `d` modulo `n`, strip or add leading zero bytes, or accept a shorter big-endian encoding.

### shared_secret()

**MUST:**

1. MUST return the x-coordinate of `d * Q` as exactly 32 bytes, keeping leading zero bytes, and nothing else: not the y-coordinate, not a hash of `Z`.
2. MUST check the private key before the public key: an input with both faults returns `InvalidPrivateKey`.
3. MUST return `InvalidPublicKey` for every encoding other than 65 bytes starting with `04`: the identity `00`, compressed points (`02`, `03`), hybrid points (`06`, `07`), raw 64-byte coordinates, truncated or extended input, and empty input. Compressed points are rejected even when they decode to a valid point, because TLS 1.3 requires the uncompressed form.
4. MUST return `InvalidPublicKey` for a coordinate that is at least `p` (a non-canonical encoding of a field element) and for a point that is not on the curve. Skipping the on-curve check enables invalid-curve attacks, which recover the private key from a few exchanges.
5. MUST NOT return a shared secret derived from an invalid public key, not even an all-zero one.

### Common

**MUST:**

1. **Constant time.** Scalar multiplication MUST run in time independent of the private key `d`: the sequence of field operations, the branches taken and the memory addresses read MUST NOT depend on the bits of `d` or on intermediate point values.
   A fixed-window or Montgomery-ladder method over a fixed number of iterations (256 bits, including leading zero bits), with table entries selected by a masked scan of the whole table, meets this. Field arithmetic MUST be constant time too: no data-dependent final subtraction branch and no early exit in modular inversion.
2. **Exceptional cases.** Addition formulas MUST give the right result when the two inputs are equal, are negatives of each other, or one is the point at infinity, as they can be during a fixed-window multiplication; complete formulas (Renes, Costello and Batina 2016) handle all of these without branches.
3. **Agreement.** For valid private keys `a` and `b`, `shared_secret(a, public_key(b)) == shared_secret(b, public_key(a))`.

**SHOULD:**

1. SHOULD overwrite intermediate points and copies of `d` before returning.

Validation of the public key is not secret-dependent and MAY branch; the error it returns reveals nothing about `d`.

## Test Vectors

`private_key_hex` and `peer_public_key_hex` are lowercase hex. A `public_key` result is the 65-byte point; a `shared_secret` result is `Z`.

### Sources

- `nist-cavs` vectors are the 25 `[P-256]` records (`COUNT = 0` to `24`) of `KAS_ECC_CDH_PrimitiveTest.txt` in NIST CAVP `ecccdhtestvectors.zip` (CAVS 14.1). Each gives a `public_key` vector (`dIUT` to `04 || QIUTx || QIUTy`) and a `shared_secret` vector (`dIUT` with `04 || QCAVSx || QCAVSy`, to `ZIUT`).
- `wycheproof-tc-N` vectors are from Project Wycheproof `testvectors_v1/ecdh_secp256r1_ecpoint_test.json` (test-case id `N`), whose public keys are bare SEC 1 points. The subset is the first 8 test cases, in tcId order, of each distinct combination of result, flags and comment; that keeps 240 of the 355 cases and every kind of case. All 355 were checked.
  Wycheproof gives private keys as minimal signed big-endian integers (33 bytes with a leading `00` when the top bit is set, and shorter for small keys); they are given here as exactly 32 bytes, left-padded with zeros.
  The one `acceptable` case (tc 2, a valid compressed point) expects `InvalidPublicKey` here, as every compressed point does. Every `valid` case expects Wycheproof's `shared`, and every `invalid` case expects `InvalidPublicKey`.
- `computed` vectors have no published source: private keys 1, 2, `n - 2` and `n - 1` with `public_key`, and with the CAVS `COUNT = 0` peer key; and the CAVS `COUNT = 0` private key with the base point `G` as the peer.
- `constructed` vectors are error cases built for this spec. The bad public keys modify the CAVS `COUNT = 0` peer key, except `x-plus-p` and `y-plus-p`, which add `p` to the small x-coordinate of Wycheproof tc 49 and the small y-coordinate of tc 50, giving 32-byte encodings of valid points with a non-canonical coordinate.
- Every expected value was computed by two independent implementations, which agreed, and matched its published source where one exists.

## Edge Cases

- **Shared secret with leading zero bytes.** `Z` is always 32 bytes; a big-integer library that drops leading zeros produces a short secret and a different TLS key schedule. Several Wycheproof `edge-case-shared-secret` vectors have small `Z`.
- **Private key 1 and `n - 1`.** `public_key(1)` is `G`; `public_key(n - 1)` is `-G`, with the same x-coordinate and `y = p - Gy`.
- **Peer key equal to `G` or to the caller's own public key.** Valid points; they are processed like any other.
- **Point with `x = 0` or `y = 1`, or small coordinates.** Valid points that exercise special cases in projective formulas (Wycheproof `edge-case-doubling`, `edge-case-ephemeral-key`).
- **Coordinate equal to `p`, or `x + p` for a small valid `x`.** `InvalidPublicKey`: field elements are encoded canonically.
- **Points on the quadratic twist or another curve.** Not on P-256: `InvalidPublicKey` (Wycheproof `wrong-curve` gives them compressed; `invalid-curve-attack` gives off-curve uncompressed points).
- **Private key with a leading `00` and 33 bytes, or 31 bytes.** `InvalidPrivateKey`: the length is exactly 32.

## Implementation Notes

- **Field arithmetic.** P-256's prime has the special form `2^256 - 2^224 + 2^192 + 2^96 - 1`, which allows fast (Solinas) reduction, but Montgomery multiplication with 64-bit limbs is simpler to make constant time and is fast enough. Keep values below `p` with a masked conditional subtraction.
- **Coordinates.** Jacobian or homogeneous projective coordinates avoid an inversion per addition; convert to affine with one inversion at the end. Compute the inversion as `z^(p - 2) mod p` with a fixed addition chain, which is constant time.
- **Complete formulas.** The Renes-Costello-Batina complete addition for `a = -3` (algorithms 4 and 5 of their paper) has no exceptional cases, so the double-and-add loop needs no branches on intermediate values. Incomplete Jacobian formulas need explicit masked handling of doubling and infinity, and the Wycheproof `edge-case-doubling` vectors catch the usual mistakes.
- **Scalar multiplication.** A 4-bit or 5-bit fixed window over all 256 bits, starting from the identity, with a constant-time table lookup, is the usual choice. Do not skip leading zero windows of `d`.
- **Public-key check order.** Check the encoding length and prefix, then the coordinate ranges, then the curve equation, all before touching the private key.
- **No point validation shortcut.** Do not rely on the scalar multiplication to "fail" on an off-curve point: formulas that do not use `b` compute a valid-looking result on another curve, which is what invalid-curve attacks exploit.
